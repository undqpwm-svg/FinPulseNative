# Приложение ФинПульс и API v1: как клиент ложится на контракт

Источник истины — контракт «ФинПульс: API приложения руководителя», v1, проект от 11.11.2026, редакция с cookie
refresh-токена, CORS и расширенной сводкой (хранится у заказчика, в публичный репозиторий не кладём). Здесь — как
приложение его использует.

> Папка `/docs` публикуется на finpulse.smartsol.pro — документацию туда не кладём.

## Где что

| Файл | Что |
|---|---|
| `docs/js/config.js` | `apiBase` (`https://api.smartsol.pro/api/v1`; тестовый — `https://api-test.smartsol.pro/api/v1`), `appVersion`, таймаут 25 с |
| `docs/js/api/server.js` | **переходник**: запросы по контракту → DTO экранов; токены; коды ошибок |
| `docs/js/api/demo.js` | те же DTO на выдуманных данных, без сети |
| `docs/sw.js` | push по формату 9.3, открытие заявки |
| `tests/server-mock.cjs` | проверка по контракту на подменённых ответах (112 проверок) |

Экраны (`screens.js`) контракта не знают: изменится контракт — правится `server.js`.

## Эндпоинты

| Экран / действие | Контракт |
|---|---|
| запуск | `GET /version` — `min_app_version` (иначе «Обновите приложение»), `webpush_public_key`. Нет связи — вход всё равно открывается |
| вход | `POST /auth/code` → `POST /auth/token` (`challenge_id`, код); `POST /auth/refresh`, `/auth/logout`, `/auth/logout-all` — без тела, по cookie |
| выбор организации | `GET /orgs`: больше одной — экран выбора, одна — сразу главная; `available: false` — пометка «нет связи с 1С» |
| главная | **один** `GET /orgs/{id}/summary`: название, `unread_count` (колокольчик), `threshold` (красные дни) |
| счета | `GET /orgs/{id}/accounts` (суммы — `balance_kzt`) |
| календарь | `GET /orgs/{id}/calendar` (по умолчанию 28 дней), порог — `threshold`, суммы позиций — `amount_kzt` |
| заявки | `GET /orgs/{id}/requests?tab=pending|decided&limit=100&cursor` (до 5 страниц), карточка, `files/{id}` |
| решения | `POST …/approve`, `…/reject` (+ `…/return` в переходнике) с `Idempotency-Key` |
| отчёты | `reports/cash-flow`, `reports/plan-fact`, `reports/debtors?limit=5` |
| уведомления | `GET /notifications?org_id`, `POST /notifications/read` (`ids`+`org_id` / `all`+`org_id`) |
| профиль | `GET/PUT /me/settings`, `GET /me` |
| push | `POST /devices` (каждый запуск, если разрешено), `DELETE /devices/{id}` |

Заголовки: `X-App-Version`, `X-App-Platform: web` — на всех запросах; `Authorization: Bearer` — кроме входа и
`/version`.

## Токены

- access-токен — только в памяти.
- refresh-токен — в cookie `HttpOnly` `fp_refresh` (`Path=/api/v1/auth`): приложение его не видит и не хранит.
  Запросы `/auth/token`, `/auth/refresh`, `/auth/logout`, `/auth/logout-all` — с `credentials: 'include'`,
  остальные — `credentials: 'omit'` и `Authorization: Bearer`.
- В `localStorage` (`finpuls-session`) — только признак входа, срок cookie и профиль для экрана. Токенов нет.
- После перезапуска access-токена нет — первым запросом идёт `POST /auth/refresh`.
- `401 token_expired` → **одно** обновление на все одновременные запросы, повтор запроса.
- `401 refresh_invalid` / `unauthorized` → признак входа удаляется, вход, «Сессия истекла — войдите снова».
- `403 access_revoked` (при входе, обновлении или запросе) → вход с текстом `message`.
- Cookie `SameSite=Strict` работает, потому что приложение и API — один сайт `smartsol.pro`. Тестовую сборку
  тоже открывать с поддомена `smartsol.pro`.

## Ошибки → что видит пользователь

| Контракт | Экран |
|---|---|
| `429 resend_too_early` | «Код уже отправлен. Новый можно запросить через N секунд» |
| `429 too_many_requests` (5 кодов за час) | «На этот номер уже отправлено 5 кодов за час. Повторите через N минут» |
| `429 phone_blocked` | на входе — «Номер заблокирован после 5 неверных кодов…»; на коде — таймер блокировки, ввод закрыт |
| `400 invalid_code` | «Неверный код. Осталось попыток: N», поле очищается |
| `400 code_expired` | «Код истёк — запросите новый» + «Отправить код ещё раз» |
| `403 access_revoked` | экран входа с текстом `message` |
| `503 source_unavailable` | при входе — «Нет связи с учётом компании. Код действует ещё N мин. Повторить» (тот же код); в данных — «1С сейчас недоступна» + «Обновить»; в решении — «решение не применено» + «Повторить» |
| `504 source_timeout` | «Сервер долго не отвечает» + «Обновить»; в решении — повтор с тем же ключом |
| `409 already_decided` | «Заявка уже согласована: `decided_by`, `decided_at`. Ваше решение не отправлено» |
| `409 not_awaiting_you` | «Нет прав на это решение» (этап сменился) + «Обновить заявку» |
| `422 action_failed` | «Учёт не принял решение» + `message`, заявка в прежнем состоянии |
| `422 comment_required` | подсветка причины отказа |
| `426 app_outdated` | «Обновите приложение» |
| `503 maintenance` | «Технические работы» |
| нет ответа | «Нет связи» + «Обновить» / «Повторить» с тем же `Idempotency-Key` |

## Что сделано на экранах под контракт

- **Дебиторка — возраст, а не просрочка.** Главная и отчёт «Должники»: «Долг по возрасту» 0–30 / 31–60 / > 60 дней
  (`aging`), у должника — «старейший документ — N дней» (`oldest_days`). Слов «просрочено» нет.
- **«На доработку»** в карточке заявки (`POST …/return`), комментарий обязателен, как при отклонении.
- **«Выйти со всех устройств»** в профиле (`POST /auth/logout-all`), с подтверждением.
- **Настройки:** переключатель с `editable: false` неактивен, подпись «Настраивает администратор»; подписи берут
  `time`, `min_amount`, `days_ahead`.
- **План-факт:** `has_plan: false` — «Бюджет на месяц не задан» и только факт; статья с `plan: null` — «факт, плана нет».
- **Push без входа:** ссылка на заявку запоминается (30 минут), после входа открывается заявка, организация берётся
  из ссылки, уведомление отмечается прочитанным.

## Что не показываем

- **Самый старый должник на главной** — в сводке его нет, строка скрыта (решение заказчика).
- **Счёт поставщика** (`invoice.items`) и **несколько статей** (`lines`, `budgets`) — показываются файлы и бюджет
  основной статьи.
