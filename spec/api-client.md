# Приложение ФинПульс и API v1: как клиент ложится на контракт

Источник истины — контракт «ФинПульс: API приложения руководителя», v1, редакция со входом «номер в приложении —
код из Telegram-бота» (`start` с номером → `poll` → `confirm`), cookie refresh-токена, CORS, расширенной сводкой и `partial` в `/orgs`
(хранится у заказчика, в публичный репозиторий не кладём). Здесь — как приложение его использует.

> Папка `/docs` публикуется на finpulse.smartsol.pro — документацию туда не кладём.

## Где что

| Файл | Что |
|---|---|
| `docs/js/config.js` | `apiBase` — рабочий `https://api.smartsol.pro/api/v1`; `apiBaseTest` — тестовый, включается адресом с `?api=test` (см. «Тестовый сервер»); `appVersion` (сейчас 1.1.1), таймаут 25 с |
| `docs/js/api/server.js` | **переходник**: запросы по контракту → DTO экранов; токены; коды ошибок |
| `docs/js/api/core.js` | ошибка `ApiError`, хранилище, `once` — склейка одинаковых GET |
| `docs/js/api/demo.js` | те же DTO на выдуманных данных, без сети |
| `docs/sw.js` | push по формату 9.3, открытие заявки |
| `tests/server-mock.cjs` | проверка по контракту на подменённых ответах; адрес API берёт из `config.js` |

Экраны (`screens.js`) контракта не знают: изменится контракт — правится `server.js`.

## Эндпоинты

| Экран / действие | Контракт |
|---|---|
| запуск | `GET /version` — `min_app_version` (иначе «Обновите приложение»), `webpush_public_key`. Нет связи — вход всё равно открывается |
| вход | номер телефона → «Получить код» → `POST /auth/telegram/start` (`{phone}`) → экран кода по `device`: `known` — «Введите код из Telegram», `new` — «Новое устройство»; поле из `code_length` цифр, кнопка «Войти через Telegram» (`bot_url`, сразу не открывается) → `POST /auth/telegram/poll` раз в `poll_interval` (только «вход жив» или отказ) → `POST /auth/telegram/confirm {challenge_id, code}` → токены; `POST /auth/refresh`, `/auth/logout`, `/auth/logout-all` — без тела, по cookie |
| выбор организации | `GET /orgs`: больше одной — экран выбора, одна (и `partial: false`) — сразу главная; `partial: true` — плашка «Часть организаций недоступна»; `503` — «Нет связи с учётом компании» + «Повторить» |
| главная | **один** `GET /orgs/{id}/summary`: название, `unread_count` (колокольчик), `threshold` (красные дни) |
| счета | `GET /orgs/{id}/accounts` (суммы — `balance_kzt`) |
| календарь | `GET /orgs/{id}/calendar` (по умолчанию 28 дней), порог — `threshold`, суммы позиций — `amount_kzt` |
| заявки | `GET /orgs/{id}/requests?tab=pending|decided&limit=100&cursor` (до 5 страниц), карточка, `files/{id}` |
| решения | `POST …/approve`, `…/reject` (+ `…/return` в переходнике) с `Idempotency-Key` |
| отчёты | `reports/cash-flow`, `reports/plan-fact`, `reports/debtors?limit=5` |
| уведомления | `GET /notifications?org_id`, `POST /notifications/read` (`ids`+`org_id` / `all`+`org_id`) |
| профиль | `GET/PUT /me/settings`, `GET /me` |
| push | `POST /devices` (каждый запуск, если разрешено), `DELETE /devices/{id}` |

Заголовки: `X-App-Version`, `X-App-Platform: web` — на всех запросах; `Authorization: Bearer` — кроме входа и
`/version`.

## Токены

- access-токен — только в памяти.
- refresh-токен — в cookie `HttpOnly` `fp_refresh` (`Path=/api/v1/auth`): приложение его не видит и не хранит.
  Запросы `/auth/*` (`telegram/start`, `telegram/poll`, `telegram/confirm`, `refresh`, `logout`, `logout-all`) — с
  `credentials: 'include'`, остальные — `credentials: 'omit'` и `Authorization: Bearer`.
- В `localStorage` (`finpuls-session`) — только признак входа, срок cookie и профиль для экрана. Токенов нет.
- Код из Telegram, `challenge_id` и введённый номер не сохраняются нигде: код живёт в поле ввода и уходит в теле
  `confirm`; номер — в поле и в памяти вкладки (`ui.loginPhone`), уходит только в теле `start`, после входа и выхода
  забывается. В журнал (консоль) не пишутся. `finpuls-tg-blocked` — только время, до которого вход закрыт.
- Метка знакомого устройства — cookie `HttpOnly` `fp_device`: приложение её не видит. Поэтому `start` тоже идёт
  с `credentials: 'include'`.
- После перезапуска access-токена нет — первым запросом идёт `POST /auth/refresh`.
- `401 token_expired` → **одно** обновление на все одновременные запросы, повтор запроса.
- `401 refresh_invalid` / `unauthorized` → признак входа удаляется, вход, «Сессия истекла — войдите снова».
- `403 access_revoked` (при входе, обновлении или запросе) → вход с текстом `message`.
- Cookie `SameSite=Strict` работает, потому что приложение и API — один сайт `smartsol.pro`. Тестовую сборку
  тоже открывать с поддомена `smartsol.pro`.

## Вход: номер в приложении, код из Telegram

- **Экран входа:** поле «Номер телефона» (`type="tel"`, `inputmode="tel"`, `autocomplete="tel"`, маска
  `+7 700 000 00 00`) и кнопка «Получить код». «8 701…», «+7 (701) 555-12-34», «7701…», «701…» приводятся к
  `+7 701 555 12 34`. До отправки проверяется форма: `+7` и десять цифр. В `start` уходит `+77015551234`.
- **`bot_url` сразу не открывается:** на знакомом устройстве код придёт сам. Бота открывает только кнопка
  «Войти через Telegram» на экране кода — обычная ссылка `target="_blank"`, новый вход она не начинает.
- **Экранов кода два — по полю `device` из ответа `start`** (от номера оно не зависит; нет поля или незнакомое
  значение — считаем `new`). На обоих: введённый номер и «Изменить номер» (назад на вход, номер остаётся в поле);
  поле из `code_length` ячеек (одно настоящее поле поверх: `inputmode="numeric"`, `autocomplete="one-time-code"`);
  «Код действует 5 минут» — подсказка без таймера (когда бот отправил код, приложение не знает); «Вставить код»
  (чтение буфера; нет такой возможности в браузере — кнопки нет); «Войти».
  - `device: "known"` — **«Введите код из Telegram»**: бот присылает код сам. Под кнопкой «Войти» — блок с текстом
    заказчика дословно («Если номер подключён, код придёт в Telegram в течение минуты. Не пришёл — нажмите „Войти
    через Telegram“ или обратитесь к администратору вашей компании.») и запасной кнопкой «Войти через Telegram».
  - `device: "new"` — **«Новое устройство»**: код сам не придёт. Сверху, над полем кода, — выделенный блок:
    «Код сам не придёт: вход с этого устройства нужно подтвердить в Telegram. Нажмите „Войти через Telegram“ — бот
    пришлёт код. При первом входе он попросит „Поделиться номером“.» и главная кнопка «Войти через Telegram».
    После нажатия экран становится про ввод кода: заголовок «Введите код из Telegram», текст «В Telegram нажмите
    на код в сообщении бота — он скопируется. Вернитесь сюда и вставьте его.», кнопка — «Открыть Telegram ещё раз».
- **Чего нет:** сообщений «номер не подключён» (об этом человеку говорит бот), признаков «код отправлен» и
  «устройство знакомо» — сервер этого не сообщает, приложение не угадывает.
- **Ввод и вставка кода:** берутся только цифры, не больше `code_length` — подходят «483 921», «483-921» и
  сообщение бота целиком. Код набран полностью — уходит сразу и один раз: лишняя цифра сверх длины тот же код
  заново не шлёт; повторить его можно кнопкой «Войти» или вставкой. Неполный код не отправляется.
- **Опрос** — раз в `poll_interval`; при возврате в приложение (`visibilitychange`, `focus`) — сразу, но не чаще
  `poll_interval`. Ответ `202 pending` на экране ничего не меняет; обрыв связи и `429` — опрос продолжается молча.
  Уходим с экрана — опрос останавливается. Пока код проверяется, ответ опроса не учитывается (после удачного
  входа опрос ответил бы `410`).
- **Лимиты сервера** (10 начал входа и 10 вводов кода за 10 минут с адреса): `start` уходит только по нажатию;
  на `429` кнопка неактивна и показывает таймер по `Retry-After` («Вход снова через 9:59»), на вводе кода — пауза
  с таймером. Автоповторов нет ни у `start`, ни у `confirm`.
- **Демо:** те же экраны. В поле уже стоит номер демо-пользователя (подойдёт любой). Первый вход — «Новое
  устройство»: «Войти через Telegram» открывает «бота» (шторка) — «Поделиться номером», затем сообщение с кодом тем
  же текстом, что у настоящего бота. Следующие входы (устройство «знакомо», до перезагрузки страницы или «Выйти
  со всех устройств») — экран «Введите код из Telegram»: «бот» присылает код сам, шторка с сообщением открывается
  через полторы секунды. Нажатие на код копирует его, «Вставить код» вставляет. Пять неверных кодов — вход
  отклонён, три таких входа подряд — блокировка на 15 минут.

### Переходный период (временно)

Пока на рабочем сервере прежняя схема, `start` номер не читает и отвечает `match_code` без `code_length`. Приложение
понимает оба ответа: есть `code_length` — экран ввода кода; нет, но есть `match_code` — прежний экран «Выберите в
Telegram число» и прежний опрос, который сам выдаёт токены (бот открывается кнопкой «Открыть Telegram»: сразу после
ответа окно уже не открыть — браузер его заблокирует). Поэтому публиковать приложение и выкладывать сервер можно не
одновременно. Временный код помечен «ВРЕМЕННО»: `telegramMatch` в `screens.js`, ветки в `startLogin` и `pollLogin`
в `api/server.js`, стиль `.tg-code`; его проверяет блок «Переходный период» в `tests/server-mock.cjs`. После выкладки
сервера на рабочий — удалить.

Версия: вход по коду — с `appVersion` **1.1.0**; экран «Новое устройство» — с **1.1.1**. Когда новый вход включат на рабочем сервере, там поднимают
`min_app_version` до `1.1.0`: приложение 1.0.0 код вводить не умеет.

## Тестовый сервер (проверка на телефонах)

- Включить: открыть приложение по адресу с `?api=test` — `https://finpulse.smartsol.pro/?api=test`.
- Вкладка ходит на `apiBaseTest` (`https://api-test.smartsol.pro/api/v1`), сверху на всех экранах жёлтая плашка
  «ТЕСТ · тестовый сервер api-test.smartsol.pro» с кнопкой «Выйти», заголовок вкладки начинается с «ТЕСТ».
- Только эта вкладка: выбор хранится в `sessionStorage`. Соседние вкладки и приложение с экрана «Домой»
  (`start_url` без параметра) — на рабочем сервере. Перезагрузка вкладки режим сохраняет.
- Выключить: «Выйти» на плашке, адрес с `?api=prod` или закрыть вкладку.
- Значение параметра сверяется только со словом `test`; адрес сервера из адресной строки не берётся.
- Рабочие данные не задеваются: признак входа и организация тестовой вкладки лежат в `sessionStorage`, а не в
  `localStorage`; cookie входа у `api-test.smartsol.pro` своя; push в тестовой вкладке выключен (подписка
  телефона одна на сайт и принадлежит рабочему серверу — её не читаем, не отправляем и не отменяем).
- Что нужно от сервера: `https://finpulse.smartsol.pro` в `allowed_origins` тестового сервера (CORS и проверка
  `Origin`). `connect-src` в CSP (`index.html`) оба адреса уже разрешает; service worker запросы к API не трогает.

## Одинаковые запросы

- **Причина залпов** (лог рабочего сервера 12.11): повторное нажатие на вкладку или кнопку, пока экран ещё
  грузится, запускало загрузку экрана заново — каждое нажатие давало новый такой же запрос, прежний не
  отменялся и не использовался. Чем медленнее отвечала 1С, тем больше нажатий. «Обновить» на экране ошибки —
  то же самое. Переключение организации в профиле перечитывало профиль (`/orgs`, `/me`, `/me/settings`).
- **Что сделано в приложении:** переход на адрес, который уже загружается, ничего не запускает (`nav.revisit` в
  `app.js`); адрес запоминается до первого ожидания, поэтому пара событий `popstate` + `hashchange` даёт одну
  загрузку; переключение организации в профиле — без запросов.
- **В слое API** (`core.once`, используется в `server.js`): пока GET не ответил, второй такой же в сеть не уходит —
  оба вызова ждут один ответ. Ключ — «метод + путь с параметрами». Ответ не запоминается. `POST`/`PUT`/`DELETE`
  и решения по заявкам не склеиваются. Склеиваются и скачивание вложения, и `GET /version`.
- Событий `visibilitychange`/`focus` вне экрана входа приложение не слушает: возврат во вкладку запросов не даёт.

| Контракт | Экран |
|---|---|
| `start`: номер пустой или неполный (до запроса) | «Введите номер телефона.» / «Введите номер полностью: +7 и десять цифр.», поле подсвечено |
| `start: 422 validation_error` | «Проверьте номер: +7 и десять цифр.», поле подсвечено |
| `start: 429 too_many_requests` | «Слишком много попыток входа с этого адреса. Повторите через N минут.», кнопка «Вход снова через M:SS» |

| `start: 503 maintenance` | «Вход временно недоступен. Повторите чуть позже.» |

| `confirm: 422 code_invalid` | «Неверный код. Осталось попыток: N» (`details.attempts_left`), поле очищено. Так же выглядит вход с неподключённым номером |

| `confirm`: нет ответа | «Нет связи с сервером. Проверьте интернет и нажмите „Войти“ ещё раз», код остаётся в поле |
| `poll`/`confirm: 409 challenge_rejected`, `wrong_code` | текст `message` («Код введён неверно несколько раз. Начните вход заново.») + «Начать заново» (тот же номер) |
| `poll`/`confirm: 409 challenge_rejected`, `blocked` | текст `message`, «Начать заново через 15:00» (таймер по `retry_after`); на экране входа — «Вход снова через …» |
| `confirm: 403 access_revoked` | текст `message` (доступ выключили после отправки кода) + «Начать заново» |
| `poll`/`confirm: 410 challenge_expired` | «Время входа вышло. Начните вход заново — бот пришлёт новый код.» |
| `poll`/`confirm: 404 not_found` | «Вход не найден. Начните заново.» |
| `poll: 429 too_many_requests` | опрос продолжается реже (`Retry-After`) |
| `poll`/`confirm: 503 source_unavailable` | «Нет связи с учётом компании. Вход отменён — начните заново через минуту» (таймер) |
| `poll`: нет ответа | опрос продолжается, на экране ничего не меняется |
| `403 access_revoked` (обновление токена, запрос данных) | экран входа с текстом `message` |
| `503 source_unavailable` | `GET /orgs` — «Нет связи с учётом компании» + «Повторить»; в данных — «1С сейчас недоступна» + «Обновить»; в решении — «решение не применено» + «Повторить» |
| `504 source_timeout` | «Сервер долго не отвечает» + «Обновить»; в решении — повтор с тем же ключом |
| `409 already_decided` | «Заявка уже согласована: `decided_by`, `decided_at`. Ваше решение не отправлено» |
| `409 not_awaiting_you` | «Нет прав на это решение» (этап сменился) + «Обновить заявку» |
| `422 action_failed` | «Учёт не принял решение» + `message`, заявка в прежнем состоянии |
| `422 comment_required` | подсветка причины отказа |
| `501 not_implemented` (этап 2: календарь, отчёты, настройки) | не ошибка: «Раздел появится в следующей версии», без «Обновить»; главная не ведёт в такой раздел (дни недели, «Календарь >», «Нам должны»); в профиле скрыты переключатели уведомлений, имя/телефон (`GET /me`) и выход — всегда |
| `426 app_outdated` | «Обновите приложение» |
| `503 maintenance` | «Технические работы» |
| нет ответа | «Нет связи» + «Обновить» / «Повторить» с тем же `Idempotency-Key` |

## Что сделано на экранах под контракт

- **Дебиторка — возраст, а не просрочка.** Главная и отчёт «Должники»: «Долг по возрасту» 0–30 / 31–60 / > 60 дней
  (`aging`), у должника — «старейший документ — N дней» (`oldest_days`). Слов «просрочено» нет.
- **«На доработку»** в карточке заявки (`POST …/return`), комментарий обязателен, как при отклонении.
- **«Выйти со всех устройств»** в профиле (`POST /auth/logout-all`), с подтверждением.
- **Настройки:** переключатель с `editable: false` неактивен, подпись «Настраивает администратор»; подписи берут
  `time`, `min_amount`, `days_ahead`.
- **План-факт:** `has_plan: false` — «Бюджет на месяц не задан» и только факт; статья с `plan: null` — «факт, плана нет».
- **Push без входа:** ссылка на заявку запоминается (30 минут), после входа открывается заявка, организация берётся
  из ссылки, уведомление отмечается прочитанным.

## Что не показываем

- **Самый старый должник на главной** — в сводке его нет, строка скрыта (решение заказчика).
- **Счёт поставщика** (`invoice.items`) и **несколько статей** (`lines`, `budgets`) — показываются файлы и бюджет
  основной статьи.

## Бюджет статьи в заявке

- Берётся строка `budgets` основной статьи (`article`). «Израсходовано» — `spent + approved_requests`.
- «Эта заявка» — доля заявки по статье `this_request`, а не вся сумма заявки; превышение — `over_by` из ответа
  (нет поля — `израсходовано + this_request − limit`). Полоска, процент и «Сверх лимита на …» в подтверждении
  согласования считаются от той же доли.
- У заявки с несколькими статьями подпись — «По статье» и пояснение «На эту статью из N приходится M».
- Для заявки с одной статьёй `this_request` равен сумме заявки — экран не меняется.
- В списке пометка «Сверх лимита» — по `over_limit` из ответа.
